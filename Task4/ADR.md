По скольку предполагается дальнейше развитие взаимодействия между подсистемами (в т.ч. кол-центром и АБС), использование брокера сообщений для передачи данных в кол-центр яыляется логичным этапом этого развития. Создание же отдельного микросервиса позволит: 
- вынести логику передачи ставок в отдельный компонент, чтобы не загружать АБС лишним функционалом; 
- задействовать команду разработки сайта. т.к. выбран язык PHP 
- в будущем дополнить микросервис функциональностую REST API для предосттавления актуальных ставок по депозитам, чтобы иметь возможность интегрировать другие подсистемы (сайт и интернет-банк)
### <a name="_bjrr7veeh80c"></a>**Альтернативы**
В качестве альтернативного решения можно выбрать загрзку ставок из АБС напрямую в СУБД CRM кол-центра, что позволит минимизировать временной лаг между обновлением ставок в АБС и их появлением в системе кол-центра. Но это решение менее гибко, в плане интеграции других подсистем (сайт, интернет-банк), в добавок на подсистему АБС ложится дополнительная функциональность, не относящаяся к АБС, так же могут быть проблемы с безопасностью.

Еще один вариант - использование электронной почты, когда сотрудникам кол-центра по расписанию на электронную почту отправляются файлы с актуальными ставками. Минусы этого варианта:
- отстуствие "историчности" данных, сделать выборку по письмам сложнее, чем по СУБД, это во многом ручная работа. 
- данные из писем не попадают автоматически в CRM, что делает работу сотрудников код-центра менее удобной. 
- есть вероятность ошибки со стороны менеджера, всегда можно случайно открыть старый файл.

**Недостатки, ограничения, риски**
- в системе появляется еще один компонент (микросервис передачи ставок)
- требуется доработка как АБС, так и CRM кол-центра
- передача ставок через микросервисы и выгрузку FTP занимает определенное время
